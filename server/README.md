# Local photo analysis server

## Current Gemini Live path (supersedes the periodic coach below)

The camera overlay now uses `src/services/live.ts` and an authenticated local `/live` WebSocket gateway in `server/live.ts`. The server holds the long-lived Gemini key and opens one persistent Gemini Live connection (`gemini-3.8-live`, configurable with server-only GEMINI_LIVE_MODEL). No API key or provider token is returned to mobile code. Local transport is plain WS on the trusted LAN; the provider transport is WSS. This prototype uses server proxying rather than direct client access with ephemeral tokens.

Client sends selected references once, then sequential 640px camera JPEGs about every 1.2 seconds (provider maximum one video frame per second; gateway drops too-frequent/buffered frames). No audio input is accepted or sent. Native audio output is generated by Gemini but discarded by the gateway; only its output transcription is forwarded for the overlay. The app does not play audio or request microphone access. No raw arbitrary upstream messages are accepted from clients.

The gateway requests one short Korean instruction at a time. It waits for turn completion before another prompt, with a minimum 3-second prompt spacing, rather than interrupting ongoing answers. No automatic reconnect/fallback. Each session is capped at 60 seconds and six starts per hour per process, with one active session. Frames and transcripts are not logged/stored. Stop, disconnect, app backgrounding, camera flip and navigation close the client/provider connection; setup/response timeouts close idle/broken connections. Token/key and origin checks, per-image/body bounds, frame ordering and backpressure apply. The regular /analyze 20/hour cap is separate.

Overlay labels source-frame age and measured capture-to-display time, hiding old instructions after 12 seconds. This is a Live network pipeline, not on-device frame processing; expo-camera still takes temporary snapshots and physical phone latency/shutter effects must be tested. A 1-fps upload does not promise 1-second instructions. Native development plan/prerequisites are in NATIVE_CAMERA_PLAN.md.

2026-11-04 verification: raw provider setup succeeded in 1145 ms without media. Through the local gateway using only agent-generated geometric images: ready in 896 ms, first partial transcription at 4768 ms (3869 ms after its triggering frame reached the gateway). A separate bounded two-turn smoke produced complete instructions at 7304 and 14484 ms from session start, with provider turn latencies 6357 and 6327 ms. These are synthetic desktop measurements, NOT phone speed or semantic-quality guarantees. No user photos were automatically resent. Native on-device analysis is NOT implemented.

Official Live reference: https://aistudio.google.com/docs/live-api/capabilities and https://aistudio.google.com/api-reference/live.

This backend is for this developer's local prototype, not public hosting. Do not expose port 8787 or the pairing token publicly.

## Setup

1. Run `npm run setup:analysis`. It creates ignored local config without overwriting an existing provider key.
2. Put your Google Gemini API key only in `server/.env.local`, after `GEMINI_API_KEY=`. Never put it in the root `.env.local`, any `EXPO_PUBLIC_*` variable, the mobile source, or chat.
3. `GEMINI_MODEL` defaults to `gemini-3.5-flash-lite`. API access/billing is separate from using the Gemini chat app. Check your provider account's spending limit before live use.
4. Run `npm run server`, then restart Expo (`npm start -- --go --lan`) so the mobile bundle receives its local pairing token.
5. Keep Mac and iPhone on the same trusted Wi-Fi. Client derives port 8787 on the Expo LAN host. For another backend set `EXPO_PUBLIC_ANALYSIS_URL` explicitly; use HTTPS outside local development. Expo tunnels do not automatically tunnel this separate server.

`.env.local` contains only a development pairing token, which is visible to the mobile bundle. It is not a production authentication scheme. The secret Gemini key is loaded from `server/.env.local` only by the Node backend. Native requests carry the pairing token; browser CORS is restricted to localhost preview.

## Behavior and data

- Health checks send no photos. No analysis is triggered by opening the app or taking a picture.
- User explicitly confirms sending the selected 1–10 references plus one current-scene photo. Client creates JPEG copies up to 1280 px on the longest edge; originals are not modified. Only base64 image data is sent, not asset IDs, original filenames, EXIF objects, or location fields. Generated temporary JPEGs are removed on a best-effort basis; original selection/capture caches may remain under Expo/OS management. Do not claim all image metadata is stripped without device verification.
- LAN transport to the Mac is HTTP for this local prototype; the Mac sends to the fixed Google Gemini HTTPS endpoint. Use a trusted local network. Server keeps request images in memory only, writes no photos or analysis results to disk, and does not log request bodies, tokens, or raw provider messages. Google Gemini's own data handling terms apply; this is not a promise of zero retention by the provider.
- Requests have a 12 MB body limit and a 1,000,000-character limit per image. There is one active analysis at a time and a 20-attempt hourly cap per server process. This limit resets on restart and is not a production quota.
- No automatic provider retries. Client cancel/disconnect aborts the upstream fetch best effort; work already processed by the provider may still be billable.
- Failures are classified into request format, key/access, unavailable model, provider capacity, network, timeout, and quota (including zero allowance). Authenticated `/health` exposes only the latest code, optional numeric provider HTTP status, and timestamp; the same sanitized fields are logged. Raw provider payloads/messages, account identifiers, photos, prompts, and keys are never included. Diagnostic state is in memory and resets on restart/success. These diagnostics do not reconstruct failures that happened before this change.
- Output separates shared/single-photo style, numbered observations, distinct scenes, composition/pose/light, scene adaptation, first next action, and uncertainty. Invalid, truncated, or refused output is not shown as a successful analysis.
- Result belongs to the specific reference list and current capture. Reference changes or a new capture invalidate it. Retake/cancel preserves the prior guide until a replacement photo is captured; camera screen can show the prior-scene guide. Reload clears in-memory results.

## Verification

## In-camera coach prototype

`src/LiveCoach.tsx` overlays instructions on the camera preview. The camera stage no longer requires scrolling to a separate guidance card. Start requires its own confirmation for repeated sampling: selected references plus a fresh camera-generated JPEG, around every 10 seconds, maximum 5 attempts per start. The existing server-wide 20/hour cap still applies. No API billing settings were changed. This is periodic snapshot coaching, NOT frame-by-frame video feedback or a completed low-latency real-time system.

References are JPEG-encoded once in memory per coaching start. Samples are serialized, timed out at 30 seconds, never queued concurrently. Stop, navigation, camera flip, loss of readiness, and app backgrounding abort the active run; errors stop rather than retry. Old asynchronous completions are ignored. Generated preview sample files are deleted best effort; regular captures are separate. Last instruction is labeled by source-frame age and hidden after 20 seconds. Short live-mode instructions are limited to 80 characters on server and client. Camera capture/flip is disabled while a preview snapshot is being taken; photo capture then leaves the camera stage and unmounts the coach.

`mode: live` uses the same validated multi-reference analysis contract, with an added prompt asking for one action directed at photographer or subject, grounded in visible differences. EV suggestions are 0.3-step experiments only, not measured exposure or automatic camera control. Preview/capture crop alignment, snapshot flash/shutter behavior, timer/cancel lifecycle, guide accuracy and on-phone layout all need physical testing. For smoother, subsecond feedback and actual exposure control, plan a native camera/frame-processing development build; do not claim those are implemented.

The free-API personal-information restriction applies to every sampled frame, including people moving into view; consent explains this. No sampling begins automatically on opening the camera or on hot reload.

`npm run typecheck`, `npm test`, and `npx expo export --platform ios --output-dir /tmp/insta-shot-ai-ios-export`.
Server tests use synthetic marker bytes and fake AI output with an injected fetch function. They never call Google Gemini or use user photos. Live provider quality, phone resizing/upload, and phone result display require an actual key and an explicit user-triggered analysis.
